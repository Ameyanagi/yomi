# Korean search-key convention

Yomi exposes four explicit modern-Hangul finder transformations:

| Function | `한글` output | Purpose |
| --- | --- | --- |
| `romanize_hangul` | `hangeul` | joined Latin query key |
| `romanize_hangul_spaced` | `han geul` | syllable-separated Latin key |
| `hangul_choseong` | `ㅎㄱ` | compatibility-choseong initials |
| `hangul_keyboard` | `gksrmf` | Korean Dubeolsik input sequence |

For ordinary candidate indexing, `korean_candidate_keys(source)` is the small
front door over those slices. It returns typed `SearchKey` values in this
stable order:

| Kind | `서울` key |
| --- | --- |
| `ORIGINAL` | `서울` |
| `KOREAN_ROMANIZED` | `seoul` |
| `KOREAN_INITIALS` | `ㅅㅇ` |
| `KOREAN_KEYBOARD` | `tjdnf` |

`max_count` is constrained to `[0, 4]`. `max_total_key_bytes` bounds the three
generated keys together while leaving the original key available, so a caller
can put a hard ceiling on indexing expansion without learning representation
details. Generation stops as soon as the count cap is full; a zero generated
byte budget returns only the original key.

Every function returns `PhoneticRepresentation`. Precomposed syllables and
canonical leading-vowel-optional-trailing Jamo clusters produce identical key
text. Each emitted syllable span maps to the complete source grapheme.
Non-Hangul graphemes pass through unchanged. A space generated by
`romanize_hangul_spaced` is explicitly unmapped; a match containing nearby
Latin text still projects to its contributing Hangul syllables, while a match
of only that separator projects to no source range.

## Deterministic romanization

The scheme is Revised-Romanization-style and syllable local. A syllable is the
concatenation of one initial, one vowel, and one optional final token:

```text
initial: g kk n d tt r m b pp s ss "" j jj ch k t p h
vowel:   a ae ya yae eo e yeo ye o wa wae oe yo u wo we wi yu eu ui i
final:   "" k k k n n n t l k m p l l p l m p p t t ng t t k t p t
```

This is deliberately a deterministic search spelling, not pronunciation
assimilation. For example, `한글` is `han geul` / `hangeul`. Contextual forms
such as `같이 -> gachi` and `신라 -> silla` are outside this version.

## Dubeolsik keyboard form

Tokens are the lowercased QWERTY keys for the Korean 2-set layout:

```text
initial: r r s e e f a q q t t d w w c z x v g
vowel:   k o i o j p u p h hk ho hl y n nj np nl b m ml l
final:   "" r r rt s sw sg e f fr fa fq ft fx fv fg a q qt t t d w c z x v g
```

Lowercasing intentionally collapses shifted tense-consonant keys for the
case-insensitive finder path, matching Yuru's established key behavior.

## Performance boundary

Each requested representation performs one grapheme scan and appends directly
to its output and mapping buffers. The unified bundle stops generating as soon
as its count or byte budget is exhausted. Profiling on Apple M4 identified
allocation and list growth, rather than scalar arithmetic, as the important
cost across CJK key generation. Hangul table selection and UTF-8 expansion are
branch-heavy, variable-length work, so this implementation intentionally does
not advertise SIMD: a vector path would add dispatch and packing without
addressing the measured bottleneck. The source-mapping contract does not expose
an execution mode.

Run `pixi run bench-search-keys` for the checked-in workload and use the
compiled-binary plus macOS `sample` procedure in `benchmarks/README.md` when
changing these paths.
